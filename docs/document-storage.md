# Document Storage

The platform owns document metadata and safe storage references. It does not expose filesystem paths to candidates or
public clients.

## Implemented

- `Document` persistence with purpose, original filename, storage key, content type, byte size, SHA-256, uploader, and
  timestamps.
- `LocalDocumentStorage` for the current filesystem-backed development/server profile.
- JD upload endpoint for draft jobs.
- Resume, photo, and introduction-video upload endpoints for public application/follow-up workflows.
- Extension and content-type validation.
- Maximum upload size enforcement.
- SHA-256 copied onto `JobRubricVersion` and `ScreeningRun` where relevant.

## Upload Policies

JD uploads allow:

- `.pdf`
- `.docx`
- `.txt`
- `.md`

Resume uploads allow:

- `.pdf`
- `.json`

Photo uploads allow:

- `.jpg`
- `.jpeg`
- `.png`

Introduction video uploads allow:

- `.mp4`
- `.webm`
- `.mov`

JSON resumes exist for synthetic structured-profile fixtures. The normal production path is a stored resume document
that the engine processes through OCR/structuring before scoring.

## Safety Rules

- Candidate-supplied paths are never accepted.
- Storage keys are generated by the platform.
- API responses omit storage keys.
- Public application document ownership may be nullable before an application exists; application-scoped follow-up
  controls access after submission.
- Staff/candidate-account document uploads still enforce uploader ownership.
- The screening worker resolves documents from platform metadata, not request paths.
- Real resumes, JDs, OCR outputs, model files, private artifacts, and secrets must not be committed.
